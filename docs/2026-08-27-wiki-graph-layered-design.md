# Wiki 图谱分层渲染预案（prototype-wiki-graph.html 路线）

日期：2026-08-27
状态：设计定稿（未实现）
对象：`docs/prototypes/prototype-wiki-graph.html`（纯手写 SVG 力导向原型）

## 背景

当前 wiki 图谱原型为单 HTML 文件：内联 `DATA` JSON + 手写 O(n²) 力导向 + SVG DOM 渲染，
每帧 `render()` 对全部节点/边/标签写 DOM 属性，`requestAnimationFrame` 无限循环。
当前数据量 86 节点 / 57 边，运行流畅。

容量估算（普通 PC）：

- 舒适区 ~300–500 节点；
- 1000 节点：斥力+碰撞两个 O(n²) 循环每帧约 100 万次迭代（10–20ms），加载时同步预跑
  900 帧会先白屏冻结数秒；
- 2000+ 节点：不可用。

参考量级：Android（AOSP）级项目的实用 wiki 约 5k–2 万条目（每个构建模块/服务一条）。
存储与检索在该量级无压力，瓶颈只在可视化层。因此需要"数据可以涨、屏幕上的图始终不大"
的预案。

约束：**沿用现有手写 SVG 方案**，不引入 Sigma/G6 等图库，保持单文件、双击即用的原型性质。

## 设计：骨架常显 + 类目下钻 + DOM 懒挂载

### 1. 数据分层（骨架 vs 叶子）

- **骨架层 L0（常显）**：`isDir` 目录节点 + `deg >= 阈值` 的枢纽节点 + 它们之间的边。
  数据量大时这层收敛到几百节点，O(n²) 物理与 SVG DOM 均在舒适区。
- **叶子层 L1（按需）**：其余节点。初始**不进 DOM、不参与物理模拟**——是完全不创建元素，
  而非现有的 `dim` 淡化（`opacity:.12` 元素仍在 DOM，节点多了照样拖垮渲染）。

分层可直接复用现有数据字段（`isDir`、`deg`），无需改数据生成侧。

### 2. 下钻交互（复用图例，改挂载语义）

现有图例点击走 `applyFilters()` 只做 `dim`。预案改为：

- 点击图例 / 双击某类目簇 → 将该类目叶子节点**创建进 DOM**，以 `focus[category]` 为
  中心做局部力导向收敛（只模拟该类目 + 骨架，几十帧即稳）；
- 再次点击收起 → 从 DOM 摘除，但**保留坐标**（`n.x/n.y` 不丢），再次展开无需重算布局；
- 顶栏加"返回总览"面包屑；搜索命中叶子节点时自动展开对应类目并高亮。

### 3. 物理模拟只跑可见集

`tick()` 的斥力/碰撞双重循环由遍历 `nodes` 改为遍历 `visibleNodes`
（骨架 + 已展开类目）。骨架预跑收敛后基本静止；展开类目只扰动局部，
直接复用现有拖拽回热机制（`alpha = Math.max(alpha, 0.25)`）。

### 4. 自动降级阈值（当前项目零感知）

`nodes.length <= 400`（阈值调试后定）→ 走现有全量模式，行为完全不变；
超过 → 自动进入分层模式。当前 86 节点项目不受任何影响，预案仅在数据涨上来时生效。

### 5. 数据文件

内联 `DATA` JSON 到数万条仅几 MB，不拆分。真到 10 万级再考虑按类目拆 JSON、
展开时 `fetch`——明确列为后话，本预案不做。

## 实现要点（改动面）

- `render()` / `tick()`：遍历可见集而非全量 `nodes`；
- 节点/标签元素改为懒创建（展开时建、收起时摘），坐标持久化在数据对象上；
- 边只渲染两端点均可见的；
- 图例交互从 `dim` 语义改为挂载/卸载语义；
- 顶栏加"返回总览"入口。

预估单文件内 100–150 行增量，零依赖。

## 非目标

- 不引入 WebGL/Canvas 图库（若未来放弃手写 SVG 路线，`prototype-wiki-graph-sigma-2k.html`
  是已验证的替代方向）；
- 不做全量"银河系图"模式——大图的正确打开方式是分层下钻，全量图只适合做壁纸；
- 不做数据文件拆分加载（10 万级以后的事）。
